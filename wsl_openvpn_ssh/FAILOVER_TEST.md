# OpenVPN-over-SSH failover test

Дата: 2026-09-12

Контролируемый тест выполнялся на активном ручном профиле
openvpn-ssh-194-130.

1. Принудительно завершён Windows SSH-forward.
2. Во время всего сбоя проверялись IPv4/IPv6 policy OUTPUT DROP.
3. Параллельно выполнялись прямые попытки HTTPS через WSL eth0.
4. Watchdog создал новый SSH-forward через 4 секунды.
5. OpenVPN снова прошёл полную проверку через 14 секунд.
6. Подтверждён выход 130.185.249.96, fail_closed=yes.
7. Ни одной прямой утечки через eth0 не обнаружено.

Дополнительно проверено ручное отключение состояния: после удаления
/run/openvpn-wsl.enabled watchdog и SSH-forward завершились, а firewall
остался DROP. Это подтверждает, что recovery не может самовольно включить
профиль без предварительной ручной команды.

Проверка полного wsl --shutdown в этом прогоне не выполнялась, чтобы не
останавливать остальные пользовательские процессы WSL. Маркер находится в
tmpfs /run и исчезает при остановке дистрибутива; watchdog также проверяет
wsl.exe --list --running до любых команд запуска.

## Проверка стабильности после устранения DNS-feedback loop

Health-check переведён на DNS-независимую проверку внешнего IP и требует две
последовательные неудачи перед перезапуском OpenVPN. После перезапуска
watchdog выполнено 12 последовательных пользовательских DNS+HTTPS проверок:
12 успешных, выход каждый раз 130.185.249.96, ложных recovery в журнале нет.

Повторное завершение SSH-forward восстановило доступ примерно за 12 секунд.
Во время сбоя IPv4/IPv6 OUTPUT оставались в policy DROP, прямая HTTPS-попытка
через eth0 не прошла. После восстановления ещё 5 из 5 обычных DNS+HTTPS
проверок успешно вышли через 130.185.249.96.

## Запуск без прав администратора

Дата повторной проверки: 2026-09-13.

Windows launchers переведены с `netsh portproxy` на прямую привязку SSH local
forward к текущему адресу WSL gateway. Полный запуск выполнен задачей Windows
с `RunLevel Limited`; внутри процесса подтверждено `IS_ADMIN=False`.

Проверено:

1. OpenVPN успешно поднялся без UAC и прав администратора.
2. Выходной адрес — `130.185.249.96`, `fail_closed=yes`.
3. После принудительного завершения SSH-forward политики IPv4 и IPv6 OUTPUT
   оставались `DROP` на протяжении всего восстановления.
4. Неадминистраторский watchdog создал новый SSH-forward и восстановил VPN.
5. Принудительные попытки выхода через `eth0` по IPv4 и IPv6 заблокированы.
6. Правила Windows `portproxy` для порта 8443 отсутствуют.
