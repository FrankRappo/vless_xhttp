# WSL -> 178 -> 104 -> 130

Испытанный кандидат WSL для выхода через отдельную цепочку:

```text
WSL (Xray XHTTP/Reality)
  -> 203.0.113.20:443, user wsl178-130
  -> 104, outbound out-104-130
  -> 104: user relay178-130
  -> 130, outbound out-130
  -> Internet, exit 198.51.100.130
```

Профиль не изменяет маршруты остальных клиентов 178: Windows/iPhone/Android продолжают использовать прежний `out-104-relay` и exit 194.

> **Текущее состояние 2026-08-19:** после инцидента активная WSL возвращена на
> прежний маршрут `WSL → 104 → 130`. Этот профиль через 178 сохранён как
> проверенный кандидат и сейчас не активен. Окончательное решение владельца —
> оставить WSL напрямую на 104→130; повторный запуск кандидата допустим только
> как отдельный контролируемый эксперимент.

## Почему WSL не переведён на 178 постоянно

1. Прямой XHTTP/Reality ClientHello из WSL проходил только после дополнительной
   `freedom.fragment`; без неё сеть возвращала Reality fallback.
2. Короткие canary были успешны, однако при расширенной эксплуатации появились
   отдельные timeout и обрыв длительной загрузки. Для постоянного рабочего
   профиля этого недостаточно.
3. Инцидент на 178 показал дополнительную связанность: зависание server-side
   XHTTP-egress и рестарт 178 требовали отдельного восстановления локального
   Xray WSL. На прямом WSL→104 этого дополнительного hop/state нет.
4. Текущий WSL→104→130 снова проверен: правильный exit `198.51.100.130`, DNS и
   YouTube работают, прямой `eth0` блокируется.
5. Сравнительный замер 3×20 МБ дал WSL→104→130 медиану `32.61 Mbit/s` и 3/3
   успешных загрузки. Владелец выбрал более простую доказанную цепочку.

Fragment-профиль, supervisor и recovery-инструменты сохранены как технический
резерв, но их наличие не означает, что профиль активен.

## Главное открытие: рабочая фрагментация XHTTP

Для этого соединения устойчиво работает фрагментация только TLS ClientHello на стороне клиента Xray:

- packets: `tlshello`;
- length: `50-100` байт;
- interval: `1-3` мс;
- фрагментация подключена через отдельный freedom outbound `fragment` и `sockopt.dialerProxy`;
- прямое транспортное соединение закреплено за `eth0`;
- обычная TCP-фрагментация соединение не восстановила.

Перед вводом в работу профиль прошёл серию: 8/8 проверок exit IP, YouTube 3/3 HTTP 200, передача 20 МБ примерно 3.3 МБ/с и повторная проверка после 30 секунд простоя.

## Файлы

- `xray-wsl-178-104-130.json` — Xray SOCKS `127.0.0.1:10810`, XHTTP/Reality до 178 и TLS ClientHello fragmentation.
- `sing-box-tun-178-104-130.json` — TUN `tun-vless178130`, передача трафика в Xray SOCKS `127.0.0.1:10810`.
- `switch-vless178-130-supervised.example.sh` — контрольная копия рабочего supervisor.
- `start-vless178130.example.sh` — контрольная копия единой команды запуска.
- `/usr/local/bin/switch-vless178-130-supervised` — установленный supervisor кандидата.
- `/usr/local/bin/start-vless178130` — штатная единая команда запуска.
- `/usr/local/bin/killswitch-vless-178` — killswitch, разрешающий через `eth0` только `203.0.113.20:443`.
- `/usr/local/bin/rollback-vless130-from-178` — полный возврат к прежней цепочке WSL -> 104 -> 130.
- `/usr/local/bin/start-vless130` — прежний рабочий запуск и аварийный откат.

JSON-файлы содержат клиентские идентификаторы и должны оставаться доступными только root.

## Почему нельзя переключать профиль из активной сетевой сессии

Старый запуск выполнялся foreground-командой из Codex внутри WSL. После применения нового killswitch и остановки старого TUN соединение Codex оборвалось. Среда завершила process scope вместе с дочерним `nohup`, поэтому 180-секундный rollback не дожил до запуска.

Переключение теперь передаётся `atd`. Job продолжает работу независимо от разрыва текущей WSL/Codex-сессии.

## Безопасный запуск

Команда контролируемого запуска кандидата (не текущий штатный WSL-профиль):

```bash
sudo /usr/local/bin/start-vless178130
```

Она сама валидирует оба JSON, не перезапускает уже активный профиль, запускает
`atd`, исключает duplicate job и передаёт переключение независимому supervisor.

Имена `/usr/local/bin/start-vless178-130` и прежнее
`start-vless178-130-with-rollback` теперь являются безопасными shim на эту же
команду. Старые foreground-версии сохранены только в `backups/`.

Supervisor напрямую из сетевой сессии не запускать. Низкоуровневый эквивалент,
который выполняет wrapper:

```bash
sudo service atd start
echo '/usr/local/bin/switch-vless178-130-supervised' | sudo at -M now
```

Состояние и журналы:

```bash
sudo cat /run/vless178130-switch.state
sudo tail -100 /tmp/vless178130-switch.log
sudo tail -100 /tmp/xray-vless178130.log
sudo tail -100 /tmp/sing-vless178130.log
```

Успешное состояние имеет вид:

```text
SUCCESS exit=198.51.100.130 direct_rc=28 ...
```

`direct_rc=28` здесь является ожидаемым результатом: прямое подключение через `eth0` заблокировано killswitch.

## Что делает новый supervisor

1. Оставляет старый TUN работающим и временно разрешает только точный транспорт `203.0.113.20:443`.
2. Добавляет host route и правило priority 8999, чтобы Xray подключался к 178 напрямую через `eth0`, а не рекурсивно через TUN.
3. Запускает новый Xray рядом со старым профилем на отдельном SOCKS-порту `10810`.
4. Выполняет preflight и требует exit `198.51.100.130` до остановки старого профиля.
5. Только после успешного preflight применяет killswitch-178, останавливает старые процессы и поднимает `tun-vless178130`.
6. Проверяет итоговый exit IP, DNS/HTTPS, YouTube и блокировку прямого `eth0`.
7. Записывает атомарный результат в `/run/vless178130-switch.state`.

### Доработки после первого сбоя supervisor

- Ожидаемая ошибка leak-test теперь выполняется внутри `if`; глобальный `ERR` trap больше не принимает корректную блокировку `eth0` за аварию.
- При любой настоящей ошибке после commit supervisor останавливает новый Xray/sing-box и выполняет полный `/usr/local/bin/rollback-vless130-from-178`.
- При ошибке до commit новый preflight-процесс и временные firewall/route правила удаляются, а старый профиль продолжает работать.
- Запуск через `atd` отделён от жизненного цикла управляющей сессии.

## Ручной rollback

Из Windows/отдельной управляющей сессии:

```powershell
wsl.exe -d Ubuntu-24.04 -u root -- /usr/local/bin/rollback-vless130-from-178
```

Из WSL, если управляющая сессия не зависит от текущего TUN:

```bash
sudo /usr/local/bin/rollback-vless130-from-178
```

Успешный rollback заканчивается сообщением о цепочке `WSL -> 104 -> 130` и тем же exit IP `198.51.100.130`.

## Быстрая проверка, если кандидат был запущен

```bash
cat /run/vless178130-switch.state
pgrep -a -f '/usr/local/bin/(xray|sing-box) run'
ip -brief addr show tun-vless178130
curl -4fsS --max-time 20 https://api.ipify.org; echo
getent ahostsv4 youtube.com | head
curl -4fsS -o /dev/null -w '%{http_code}\n' https://www.youtube.com/
```

Leak-test должен завершиться ошибкой/timeout:

```bash
curl -4fsS --interface eth0 --connect-timeout 4 --max-time 6 https://api.ipify.org
```
