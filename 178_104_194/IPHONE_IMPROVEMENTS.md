# Возможные улучшения iPhone — пока НЕ применены

**Текущее решение:** оставить рабочую ссылку
`iphone-178-104-194.txt` с `XHTTP packet-up` без дополнительных параметров.

Цель будущих улучшений:

1. VPN-extension остаётся поднятым;
2. зависшее H2/TCP-соединение обнаруживается и заменяется внутри core;
3. при недоступности proxy трафик блокируется, а не выходит напрямую;
4. foreground-приложение не требуется перезапускать вручную.

## 1. Что уже сделано

- отдельный UUID `iphone178`;
- XHTTP `packet-up` на участке iPhone→178;
- inbound 178 `mode:auto`;
- server-side TCP keepalive на 178: idle 15 / interval 10 секунд;
- только relay-маршрут 178→104, без прямого client fallback;
- 104→194 использует штатный проверенный пул `tunnel-1…10`.

`packet-up` выбран потому, что upload состоит из коротких запросов и лучше
переживает смену сети, чем один непрерывный upload `stream-one`.

## 2. Ограничение обычной VLESS-ссылки

`vless://` надёжно переносит адрес, UUID, Reality и основные XHTTP-поля
(`path`, `mode`). Он не гарантирует одинаковый импорт расширенного блока
`extra.xmux` разными iOS-приложениями.

Поэтому нельзя безопасно добавить в текущую ссылку универсальный параметр
`reconnect=true`: такого стандартного Xray-параметра нет. Автовосстановление
зависит от используемого core и Network Extension приложения.

## 3. Кандидат A — расширенный клиентский Xray JSON

Применять только после выбора iOS-приложения, которое действительно импортирует
полный Xray JSON. Это **не серверный конфиг** и сейчас нигде не активирован.

Синтаксис приведённого блока проверен 2026-08-18 командой `xray run -test` на
Windows Xray `26.2.4`: `Configuration OK`. Это подтверждает схему JSON, но не
совместимость импорта конкретным iOS-приложением/его встроенным core.

Кандидат транспортного блока:

```json
{
  "network": "xhttp",
  "security": "reality",
  "sockopt": {
    "tcpKeepAliveIdle": 15,
    "tcpKeepAliveInterval": 10
  },
  "xhttpSettings": {
    "path": "/ru-feed/api/v3",
    "mode": "packet-up",
    "extra": {
      "xmux": {
        "maxConcurrency": "16-32",
        "maxConnections": 0,
        "cMaxReuseTimes": 0,
        "hMaxRequestTimes": "600-900",
        "hMaxReusableSecs": "300-600",
        "hKeepAlivePeriod": 15
      }
    }
  }
}
```

Ожидаемый эффект:

- клиентский TCP keepalive быстрее обнаруживает исчезнувший путь;
- H2 read-idle/keepalive быстрее закрывает молчащий transport;
- новые HTTP-запросы периодически перестают назначаться на старое H2-соединение;
- следующий запрос создаёт новый transport внутри того же VPN-extension.

Цена:

- больше keepalive-трафика и TLS/H2 handshakes;
- немного выше расход батареи;
- параметры требуют проверки на конкретной версии iOS core;
- существующее прикладное соединение (например уже зависший видеопоток) может
  потребовать повторного HTTP-запроса, хотя VPN-extension останется активным.

Официальное описание XHTTP/XMUX рекомендует по умолчанию не задавать
`hKeepAlivePeriod` вручную и использует более длинную ротацию. Здесь `15` и
`300-600` — осознанный агрессивный canary для плохой мобильной сети, а не
универсальный production-default:
<https://github.com/XTLS/Xray-core/discussions/4113>.

## 4. Кандидат B — fail-closed клиентский JSON

Для защиты от прямой утечки полный конфиг должен дополнительно обеспечивать:

- один разрешённый outbound `proxy`;
- `blackhole` для запрещённых направлений;
- отсутствие `freedom/direct` fallback;
- default routing TCP/UDP → `proxy`;
- DNS только через tunnel;
- IPv6 → blackhole, если приложение не туннелирует IPv6 корректно;
- TUN/default route без bypass для обычного Internet-трафика.

Это защищает при отказе **удалённого Xray-маршрута**, пока iOS VPN-extension
остаётся подключённым: трафик должен остановиться, а не уйти напрямую.

Это не может гарантировать fail-closed, если iOS полностью остановила или
удалила сам VPN-extension. Настоящий системный Always-On VPN, при котором iOS
дропает трафик до подъёма tunnel, Apple предоставляет для supervised/MDM
устройств: <https://developer.apple.com/documentation/networkextension/routing-your-vpn-network-traffic>.

VPN On Demand не обязан открывать foreground-приложение: он запускает/поднимает
Network Extension по системному правилу. Но его точные возможности зависят от
приложения.

## 5. Кандидат C — второй entry и автоматический failover

Если нужна устойчивость не только к зависшему соединению, но и к недоступности
всего IP 178 из Китая, лучший инфраструктурный шаг — второй независимый entry
VPS:

```text
iPhone VPN-extension
  ├─ primary: entry 178 → 104 → 194
  └─ backup:  second entry → 104 → 194
```

Клиентский core должен держать health-check/url-test и направлять **новые**
соединения на доступный outbound. При этом оба outbounds остаются proxy, direct
fallback не добавляется.

Прямой 104 можно использовать только как аварийный кандидат для теста, но он уже
показал плохую доступность из Китая и не считается полноценной независимой
резервной точкой.

## 6. Что сервер 178 сделать не может

Сервер не может сам заставить iPhone открыть новый клиентский H2 transport,
если клиентский core считает старую сессию живой. Уменьшение server-side timeout
может быстрее закрыть серверную половину, но не является гарантированным
автореконнектом клиента.

Также H2 PING поддерживает транспортное соединение, но не лечит все варианты
зависшего application stream. В Xray отдельно зафиксировано ограничение
`packet-up`: для молчащего download GET нет универсального client-side reopen /
dead-download watchdog. Это особенно заметно за CDN/reverse proxy:
<https://github.com/XTLS/Xray-core/issues/6554>.

В текущей цепочке Reality идёт напрямую до 178, без CDN, поэтому этот конкретный
CDN timeout не является текущей архитектурой, но ограничение core важно помнить.

## 7. Что не следует делать

- не добавлять `mux.cool` поверх XHTTP;
- не добавлять direct/freedom как «аварийный» выход — это создаст утечку IP;
- не задавать XMUX на сервере как способ клиентского reconnect: XMUX здесь
  клиентский механизм;
- не уменьшать таймауты одновременно на клиенте и сервере без canary;
- не заменять рабочую ссылку до теста нового конфига на конкретном приложении;
- не считать `connIdle` гарантией смены underlying H2: это timeout логического
  proxy-request, а не всего HTTP/2 transport.

## 8. Canary-план для будущего улучшенного конфига

1. Оставить текущую `iphone-178-104-194.txt` как мгновенный rollback.
2. Создать второй iPhone UUID и отдельный профиль `iphone178-canary`.
3. Проверить JSON командой `xray run -test` на той же версии core, что использует
   приложение.
4. Убедиться, что в конфиге нет direct/freedom и DNS bypass.
5. Тесты на реальном iPhone:
   - 15 минут idle;
   - блокировка экрана на 5–10 минут;
   - Wi-Fi → LTE → Wi-Fi;
   - airplane mode на 10 секунд;
   - недоступность entry 178 на 30–60 секунд.
6. Во время каждого теста проверять внешний IP и отсутствие трафика при отказе.
7. Критерий успеха: VPN-extension не отключается, при отказе Internet блокируется,
   после восстановления новые соединения работают без ручного перезапуска app.
8. При любом direct IP/нестабильности вернуть текущую packet-up-ссылку.

## 9. Приоритет улучшений

1. **Сейчас:** ничего не менять — рабочая схема важнее эксперимента.
2. Уточнить конкретное iOS-приложение и версию встроенного core.
3. Проверить поддержку полного JSON и fail-closed routing.
4. Сделать отдельный canary с клиентским XMUX/keepalive.
5. При необходимости настоящей инфраструктурной отказоустойчивости добавить
   второй entry VPS.
6. Если требуется формальная гарантия zero-leak при падении extension —
   supervised iPhone + MDM Always-On VPN.
