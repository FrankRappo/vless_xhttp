# 178 → 104 → 194: профили устройств

Цепочка для доступа из Китая:

```text
устройство → 203.0.113.20:443 → 203.0.113.10:443
           → tunnel-balancer (tunnel-1…10) → 203.0.113.30 → Internet
```

Ожидаемый внешний IP: `203.0.113.30`.

## Ссылки

| Устройство | Файл | Режим первого участка |
|---|---|---|
| Windows | `windows-178-104-194.txt` | `XHTTP stream-one` |
| iPhone | `iphone-178-104-194.txt` | `XHTTP packet-up` |
| Android | `android-178-104-194.txt` | `XHTTP stream-one` |

У каждого устройства отдельный UUID. На 178 эти пользователи различимы как
`win178-test`, `iphone178` и `android178`.

Дополнительная Windows-ссылка с другим exit:

| Устройство | Файл | Цепочка | Exit IP |
|---|---|---|---|
| Windows | `windows-178-104-149.txt` | `178 → 104 → 149` | `203.0.113.40` |

Этот профиль использует отдельного пользователя `win178-149` и не меняет
три профиля с exit 194. Полная схема и серверные образцы:
[`../wsl_149/README.md`](../wsl_149/README.md).
Работа ссылки на реальном Windows подтверждена владельцем 2026-08-20.

## Изоляция серверных веток

С 2026-08-19 основной Xray на 178 передаёт обычный трафик локальному
`xray-egress-194.service` через SOCKS `127.0.0.1:11041`. Ветка 130 работает
отдельным `xray-egress-130.service` на `127.0.0.1:11042`. С 2026-08-20
Windows-профиль с exit 149 также вынесен в `xray-egress-149.service`
на `127.0.0.1:11043`; его ссылка лежит в [`../wsl_149/`](../wsl_149/).
Health-check каждые 10 секунд перезапускает только неисправную ветку.
Операции и разбор инцидента:
[`EGRESS_ISOLATION.md`](./EGRESS_ISOLATION.md).

## Почему режимы разные

- Windows и Android используют `stream-one`, как основной давно работающий набор
  профилей на 104.
- iPhone использует `packet-up`, как два специальных профиля
  `iphone-packetup*.txt`: короткие upload-запросы лучше переживают фон и смену
  Wi-Fi/LTE, чем один долгий upload-поток.
- Инбаунд 178 имеет `mode: auto`, поэтому оба типа работают одновременно.
- Серверные участки 178→104 и 104→194 не зависят от типа устройства. На 104
  `relay178-test` попадает в штатный catch-all и распределяется только по
  `tunnel-1…10` с выходом 194.

## Импорт

- **Windows:** актуальный v2rayN; импортировать строку из
  `windows-178-104-194.txt`.
- **iPhone:** Streisand или v2RayTun; импортировать строку из
  `iphone-178-104-194.txt`. Включить VPN On Demand / автоматическое
  переподключение, если приложение предоставляет такую настройку.
- **Android:** актуальный v2rayNG или v2RayTun; импортировать строку из
  `android-178-104-194.txt`. Разрешить приложению работу в фоне и убрать
  ограничение расхода батареи.

Не включать дополнительный `mux.cool`: XHTTP уже управляет своими HTTP/2
соединениями. Экспериментальный XMUX намеренно не зашит в share-ссылки, потому
что мобильные клиенты импортируют его неодинаково.

Текущую iPhone-ссылку оставляем без изменений, пока она работает. Возможные
клиентские keepalive/XMUX, fail-closed и второй entry подробно разобраны в
[`IPHONE_IMPROVEMENTS.md`](./IPHONE_IMPROVEMENTS.md); все они помечены как
**не применённые**.

## Серверные настройки устойчивости

- 178 inbound: `mode=auto`, эффективный server TCP keepalive
  `tcpKeepAliveIdle=15` / `tcpKeepAliveInterval=10`. Историческое верхнеуровневое
  `hKeepAlivePeriod=30` не считаем клиентским reconnect-механизмом.
- Основной `xray.service` на 178 запускается как `nobody:nogroup`; боевой
  `/usr/local/etc/xray/config.json` обязан иметь `root:nogroup 0640`. Drop-in
  `20-config-permissions.conf` восстанавливает эти права перед каждым стартом и
  включает `Restart=always`; контрольная копия —
  `xray-main-hardening.conf.example`.
- 104 inbound: `mode=auto`; дальнейший маршрут — существующий пул из десяти
  туннелей, без отдельной iPhone-маршрутизации.
- Изменения профиля требуют только повторного импорта ссылки; 104 и 194
  перезапускать не нужно.
