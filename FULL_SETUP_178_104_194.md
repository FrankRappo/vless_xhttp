# Полная схема China relay: 178 → 104 → 194

**Статус:** production/canary, работает с 2026-08-18.
**Главный принцип:** существующая production-цепочка 104→194 не заменялась;
178 добавлен только как первый hop для доступа из Китая.

## 1. Архитектура

```text
Windows  -- XHTTP stream-one --┐
Android  -- XHTTP stream-one --┤
iPhone   -- XHTTP packet-up  --┘
                 │ Reality, :443, SNI www.example.org
                 ▼
        203.0.113.20 (China entry relay)
                 │ VLESS + Reality + XHTTP stream-one
                 ▼
        203.0.113.10:443 (production entry)
                 │ catch-all → tunnel-balancer
                 ▼
       tunnel-1…tunnel-10 (10 SSH-forward каналов)
                 ▼
        203.0.113.30 (production exit)
                 ▼
              Internet
```

Ожидаемый внешний IP для всех трёх профилей: `203.0.113.30`.

## 2. Профили устройств

Каталог: [`178_104_194/`](./178_104_194/)

| Устройство | Файл | Режим до 178 | Пользователь на 178 |
|---|---|---|---|
| Windows | `windows-178-104-194.txt` | `stream-one` | `win178-test` |
| iPhone | `iphone-178-104-194.txt` | `packet-up` | `iphone178` |
| Android | `android-178-104-194.txt` | `stream-one` | `android178` |

UUID находятся только в share-файлах и боевом конфиге. В документации они не
дублируются. На 104 все три устройства видны как один серверный клиент
`relay178-test`.

Выбор режимов основан на существующей production-практике:

- Windows/Android — `stream-one`, как основной стабильный набор профилей 104;
- iPhone — `packet-up`, как два специальных профиля `iphone-packetup*.txt`,
  созданных из-за зависаний при фоне и смене Wi-Fi/LTE;
- inbound 178 работает в `mode:auto`, поэтому принимает оба режима одновременно.

|---|---|

| API | `127.0.0.1:10085` |

| Main outbound | SOCKS `127.0.0.1:11041` |

| Start hardening | drop-in `20-config-permissions.conf`: восстановление прав перед стартом, `Restart=always`, `RestartSec=2s` |

Routing на 178:

- IPv6 destinations → blackhole;
- пользователь `win178-149` → `out-104-149`/SOCKS `127.0.0.1:11043` → `exit149-2` на 104 → exit `203.0.113.40`;
- пользователь `wsl178-130` → `out-104-130`/SOCKS `127.0.0.1:11042`;
- остальные пользователи `in-cn-xhttp` → `out-104-relay`/SOCKS `127.0.0.1:11041`;
- прямого freedom-fallback для клиентского трафика нет.

Поле `hKeepAlivePeriod:30` сохранено в текущем xhttpSettings, но **не считается
механизмом восстановления iPhone**: в актуальной схеме Xray H2 keepalive/XMUX —
клиентская настройка. Эффективная серверная защита — раздельные процессы egress и
`xray-egress-health.timer`: проверка каждые 10 секунд, targeted restart после
двух последовательных сбоев. См. `178_104_194/EGRESS_ISOLATION.md`.

## 8. Операционные команды

На 178:

```bash
systemctl status xray --no-pager
/usr/local/bin/xray run -test -c /usr/local/etc/xray/config.json
ss -ltnp | grep -E ':443|:10085'
jq '[.inbounds[]|select(.tag=="in-cn-xhttp")][0]
    | {users:[.settings.clients[].email],xhttp:.streamSettings.xhttpSettings}' \
   /usr/local/etc/xray/config.json
```

На 104:

```bash
systemctl status xray --no-pager
/opt/xray/xray run -test -c /etc/xray/config.json
grep 'email: relay178-test$' /var/log/xray-access.log | tail
cat /run/balancer-leak-check.heartbeat
jq -r '[.outbounds[].tag|select(startswith("tunnel-"))]|sort|join(" ")' \
   /etc/xray/config.json
```

SSH-реквизиты и jump-порядок остаются в [`AUDIT.md`](./AUDIT.md) и
[`OPERATIONS.md`](./OPERATIONS.md); здесь секреты не дублируются.

## 9. Что сейчас намеренно не меняем

- не добавляем XMUX в share-ссылки;
- не меняем server-to-server `stream-one`;
- не создаём отдельные 104-outbound для каждого устройства;
- не меняем пул `tunnel-1…10`;
- не включаем прямой fallback на 178 или клиенте;
- не перезапускаем production Xray на 104;
- не включаем автоматический rollback старого сломанного профиля 178.

Возможные улучшения iPhone описаны отдельно:
[`178_104_194/IPHONE_IMPROVEMENTS.md`](./178_104_194/IPHONE_IMPROVEMENTS.md).
